# System Migration & Security Audit

## ASP.NET Core Identity — Custom Auth Migration Completion

---

## 1. Executive Summary

The authentication layer of the Harfi platform was originally built on a **custom authentication system** that interacted directly with the `Users` table via Entity Framework Core and generic repositories. As the platform grew, this approach introduced several structural risks:

- **Bypassed Identity pipeline** — password hashing, security stamps, email confirmation, and concurrency tokens were not consistently applied.
- **Silent data loss** — the `UserService.Update` method called `DbSet.Update()` without ever invoking `SaveChangesAsync()`, meaning profile edits were accepted by the API but never persisted.
- **Runtime crashes** — navigation properties (`c.User`) were dereferenced without eager loading, producing `NullReferenceException` at runtime.
- **Unsecured endpoints** — four controllers (Admin, Users, Craftsmen, AI) had zero authorization attributes, exposing sensitive operations to unauthenticated requests.

Both **Email Confirmation** and **Phone Number Confirmation** now use ASP.NET Core Identity's official token pipeline. The `EmailConfirmed` and `PhoneNumberConfirmed` columns (inherited from `IdentityUser<int>`) are flipped to `1` exclusively through `UserManager.ConfirmEmailAsync` and `UserManager.ChangePhoneNumberAsync` respectively — never through direct property assignment.

This document details every refactoring applied to migrate fully onto **ASP.NET Core Identity** and secure the system.

---

## 2. Core Verification Flows — Unified Strategy

Both verification flows follow an identical two-layer pattern:

1. **User-facing layer**: A human-friendly 6-digit OTP code is generated, stored, sent via email/SMS, and validated by the client.
2. **Identity layer**: An ASP.NET Core Identity token (opaque, cryptographically generated) is stored alongside the OTP. After the OTP is validated, the Identity token is passed to the official `UserManager` method, which is the **only** path that sets the corresponding `Confirmed` column to `1`.

This ensures that even if the custom OTP table were tampered with, Identity's token validation would reject the request.

### 2.1 Email Confirmation

#### Problem
The `VerifyEmailAsync` method validated a custom 6-digit code against the `EmailVerification` table, then set `user.IsVerified = true` manually via `_userManager.UpdateAsync()`. Because this bypassed Identity's token validation pipeline, the `EmailConfirmed` column (inherited from `IdentityUser<int>`) was never flipped to `true`. The database column remained `0` regardless of successful verification.

#### Solution

Three methods were modified to integrate Identity's token-based confirmation:

**`EmailVerification` entity** — A new `IdentityToken` column stores the token generated by `UserManager.GenerateEmailConfirmationTokenAsync`:

```csharp
// Harfi.Models/Entities/EmailVerification.cs
public string? IdentityToken { get; set; }
```

**`RegisterAsync`** — Generates an Identity email token at registration time and stores it alongside the custom 6-digit code:

```csharp
var identityToken = await _userManager.GenerateEmailConfirmationTokenAsync(user);
var code = new Random().Next(100000, 999999).ToString();
await _verificationRepo.AddAsync(new EmailVerification
{
    UserId = user.Id,
    Code = code,
    IdentityToken = identityToken,
    ExpiresAt = DateTime.UtcNow.AddMinutes(10),
    IsUsed = false
});
```

**`VerifyEmailAsync`** — After validating the custom 6-digit code, calls `UserManager.ConfirmEmailAsync` which:
1. Cryptographically validates the Identity token
2. Sets `EmailConfirmed = true` on the `User` entity
3. Persists the change through Identity's `SaveChangesAsync`

```csharp
// 1. Mark custom code as used
verification.IsUsed = true;
_verificationRepo.Update(verification);

// 2. Identity confirmation — flips EmailConfirmed column
var confirmResult = await _userManager.ConfirmEmailAsync(user, verification.IdentityToken!);

if (!confirmResult.Succeeded)
{
    var errors = string.Join("; ", confirmResult.Errors.Select(e => e.Description));
    throw new InvalidOperationException($"Email confirmation failed: {errors}");
}

// 3. Preserve custom business logic
user.IsVerified = true;
await _userManager.UpdateAsync(user);
```

**`ResendVerificationCodeAsync`** — Generates a fresh Identity token for each new code:

```csharp
var identityToken = await _userManager.GenerateEmailConfirmationTokenAsync(user);
```

### 2.2 Phone Number Confirmation

#### Problem
No phone verification system existed. The `PhoneNumberConfirmed` column (inherited from `IdentityUser<int>`) was never set to `1`. The custom `Phone` field on the `User` entity was populated during registration but never cryptographically verified.

#### Solution

A full phone verification system was built from scratch following the exact same dual-layer pattern as email verification.

**`PhoneVerification` entity** — Mirrors `EmailVerification` with an additional `PhoneNumber` column to track which number is being verified:

```csharp
// Harfi.Models/Entities/PhoneVerification.cs
public class PhoneVerification
{
    public int Id { get; set; }
    public int UserId { get; set; }
    public string PhoneNumber { get; set; } = null!;
    public string Code { get; set; } = null!;

    /// <summary>Identity token for UserManager.ChangePhoneNumberAsync</summary>
    public string? IdentityToken { get; set; }

    public DateTime ExpiresAt { get; set; }
    public bool IsUsed { get; set; } = false;
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;

    public User User { get; set; } = null!;
}
```

**`SendPhoneVerificationCodeAsync`** — Generates an Identity phone change token and stores it with the 6-digit OTP:

```csharp
var identityToken = await _userManager.GenerateChangePhoneNumberTokenAsync(user, dto.PhoneNumber);
var code = new Random().Next(100000, 999999).ToString();

await _phoneVerificationRepo.AddAsync(new PhoneVerification
{
    UserId = user.Id,
    PhoneNumber = dto.PhoneNumber,
    Code = code,
    IdentityToken = identityToken,
    ExpiresAt = DateTime.UtcNow.AddMinutes(10),
    IsUsed = false
});
await _phoneVerificationRepo.SaveChangesAsync();

// TODO: Replace with actual SMS gateway
await _emailService.SendVerificationCodeAsync(user.Email!, user.Name, $"📱 Phone OTP: {code}");
```

**`VerifyPhoneAsync`** — After validating the 6-digit OTP, calls `UserManager.ChangePhoneNumberAsync` which:
1. Cryptographically validates the Identity token against the phone number
2. Sets `user.PhoneNumber` to the verified number
3. Sets `PhoneNumberConfirmed = true`
4. Regenerates the `SecurityStamp`
5. Persists everything through Identity's `SaveChangesAsync`

```csharp
// 1. Mark custom code as used
verification.IsUsed = true;
_phoneVerificationRepo.Update(verification);

// 2. Identity confirmation — flips PhoneNumberConfirmed column
var confirmResult = await _userManager.ChangePhoneNumberAsync(
    user, verification.PhoneNumber, verification.IdentityToken!);

if (!confirmResult.Succeeded)
{
    var errors = string.Join("; ", confirmResult.Errors.Select(e => e.Description));
    throw new InvalidOperationException($"Phone confirmation failed: {errors}");
}

// 3. Sync custom Phone field with the verified number
user.Phone = verification.PhoneNumber;
await _userManager.UpdateAsync(user);
```

**`ResendPhoneVerificationCodeAsync`** — Invalidates old unused codes, generates a fresh Identity token and OTP:

```csharp
var identityToken = await _userManager.GenerateChangePhoneNumberTokenAsync(user, dto.PhoneNumber);
```

#### DTOs Created

| DTO | Endpoint | Fields |
|-----|----------|--------|
| `SendPhoneVerificationDto` | `POST /api/auth/send-phone-code` | `Email` (required, email), `PhoneNumber` (required, phone, max 20) |
| `VerifyPhoneDto` | `POST /api/auth/verify-phone` | `Email`, `PhoneNumber`, `Code` (required, exactly 6 digits) |
| `ResendPhoneCodeDto` | `POST /api/auth/resend-phone-code` | `Email`, `PhoneNumber` |

## 3. Architecture & Service Refactoring

### 3.1 Identity Bypass Resolution — UserService Refactor

#### Problem
`UserService` injected `IGenericRepository<User>`, allowing direct reads and writes to the `Users` table via EF Core's `DbSet<User>`. This completely bypassed Identity's `UserManager`, circumventing normalization, concurrency checks (`ConcurrencyStamp`), and security stamp regeneration. Additionally, the `Update` method never called `SaveChangesAsync`, causing profile edits to be silently discarded.

#### Solution
Replaced the generic repository injection with `UserManager<User>`:

**Before:**
```csharp
public class UserService : IUserService
{
    private readonly IGenericRepository<User> _userRepository;

    public UserService(IGenericRepository<User> userRepository)
    {
        _userRepository = userRepository;
    }

    public async Task<bool> UpdateUserProfileAsync(int userId, UpdateUserDto dto)
    {
        var user = await _userRepository.GetByIdAsync(userId);
        // ... update properties ...
        _userRepository.Update(user);       // ❌ Never calls SaveChangesAsync
        return true;                        // ❌ Always returns true regardless
    }
}
```

**After:**
```csharp
public class UserService : IUserService
{
    private readonly UserManager<User> _userManager;

    public UserService(UserManager<User> userManager)
    {
        _userManager = userManager;
    }

    public async Task<bool> UpdateUserProfileAsync(int userId, UpdateUserDto dto)
    {
        var user = await _userManager.FindByIdAsync(userId.ToString());
        if (user == null) return false;

        user.Name = dto.Name;
        user.Phone = dto.Phone;
        // ...

        var result = await _userManager.UpdateAsync(user); // ✅ Persists + validates
        return result.Succeeded;                            // ✅ Reports actual outcome
    }
}
```

**Benefits gained:**
- Identity's `ConcurrencyStamp` is now checked on every write
- `SecurityStamp` is regenerated appropriately
- `UpdateAsync` internally calls `SaveChangesAsync` — no more silent data loss
- Return value reflects the actual database result

### 3.2 Data Integrity — Eager Loading of User Navigation Property

#### Problem
Two services accessed `craftsman.User?.Name`, `craftsman.User?.Email`, and `craftsman.User?.Phone` without ensuring the `User` navigation property was loaded. The `GenericRepository.GetAllAsync()` uses `AsNoTracking().ToListAsync()` with no `.Include()` calls, and `GetByIdAsync()` uses `FindAsync()` which does not follow navigation paths. Both resulted in **null navigation properties** throwing `NullReferenceException` at runtime when mapped to DTOs.

#### Solution

**`CraftsmanService.GetCraftsmanProfileAsync`** — Uses `LoadReferenceAsync` (available on `IGenericRepository<T>`) to eagerly load the User navigation after fetching the tracked entity:

```csharp
var craftsman = await _craftsmanRepository.GetByIdAsync(id);
if (craftsman == null) return null;

await _craftsmanRepository.LoadReferenceAsync(craftsman, c => c.User);
// craftsman.User is now populated
```

**`AdminService.GetPendingCraftsmenAsync`** — A new dedicated method `GetAllWithUserAsync` was added to `ICraftsmanRepository` with an explicit `.Include(c => c.User)`:

```csharp
// ICraftsmanRepository.cs
Task<IEnumerable<Craftsman>> GetAllWithUserAsync();

// CraftsmanRepository.cs
public async Task<IEnumerable<Craftsman>> GetAllWithUserAsync()
{
    return await _context.Craftsmen
        .Include(c => c.User)
        .ToListAsync();
}
```

The service was updated to call this method instead of `GetAllAsync()`:

```csharp
var allCraftsmen = await _craftsmanRepository.GetAllWithUserAsync();
```

### 3.3 Repository Implementation — UpdateAsync & DeleteAsync

#### Problem
`CraftsmanRepository` declared `UpdateAsync` and `DeleteAsync` in its interface but left both throwing `NotImplementedException`. Three production code paths called these methods:

| Caller | Method Called | Consequence |
|--------|--------------|-------------|
| `AdminService.ApproveCraftsmanAsync` | `UpdateAsync` | 💥 Crash on admin approval |
| `AdminService.RejectCraftsmanAsync` | `DeleteAsync` | 💥 Crash on admin rejection |
| `CraftsmanService.UpdateCraftsmanAsync` | `UpdateAsync` | 💥 Crash on profile update |

#### Solution

```csharp
public async Task<bool> UpdateAsync(Craftsman craftsman)
{
    _context.Craftsmen.Update(craftsman);
    await _context.SaveChangesAsync();
    return true;
}

public async Task DeleteAsync(int craftsmanId)
{
    var craftsman = await _context.Craftsmen.FindAsync(craftsmanId);
    if (craftsman is not null)
    {
        _context.Craftsmen.Remove(craftsman);
        await _context.SaveChangesAsync();
    }
}
```

## 5. Database Migrations

Two sequential EF Core migrations were applied:

### Migration 1: `AddIdentityTokenToEmailVerification`

Adds the `IdentityToken` column to the existing `EmailVerifications` table for Identity token storage:

```bash
dotnet ef migrations add AddIdentityTokenToEmailVerification \
    --project Harfi.Repositories \
    --startup-project Harfi.API
```

```sql
ALTER TABLE EmailVerifications
ADD IdentityToken nvarchar(max) NULL;
```

### Migration 2: `AddPhoneVerification`

Creates the `PhoneVerifications` table to support the new phone number verification flow:

```bash
dotnet ef migrations add AddPhoneVerification \
    --project Harfi.Repositories \
    --startup-project Harfi.API
```

```sql
CREATE TABLE PhoneVerifications (
    Id              int             NOT NULL IDENTITY,
    UserId          int             NOT NULL,
    PhoneNumber     nvarchar(max)   NOT NULL,
    Code            nvarchar(max)   NOT NULL,
    IdentityToken   nvarchar(max)   NULL,
    ExpiresAt       datetime2       NOT NULL,
    IsUsed          bit             NOT NULL DEFAULT 0,
    CreatedAt       datetime2       NOT NULL DEFAULT GETUTCDATE(),
    CONSTRAINT PK_PhoneVerifications PRIMARY KEY (Id),
    CONSTRAINT FK_PhoneVerifications_Users_UserId
        FOREIGN KEY (UserId) REFERENCES Users(Id) ON DELETE CASCADE
);
```

To apply both migrations:

```bash
dotnet ef database update \
    --project Harfi.Repositories \
    --startup-project Harfi.API
```
